# Architecture change: from a single-PC POS to a client/server shop system

**Status:** written before any code changed, as the phase requires. This document is the record of what the
re-architecture keeps, changes and removes, and of one structural decision that the brief's own MIGRATION RULE
forces: the repository is *not* moved into `apps/` and `packages/` in one sweep. Why, and what is done instead,
is in [The directory layout](#the-directory-layout-what-is-moved-and-what-is-not) below.

The reader this is written for is the next person to open the repository, who needs to know which parts of the
old single-PC design are load-bearing and which are being dismantled deliberately.

## The change in one paragraph

Infoflex today is one Electron application that owns the SQLite file and does everything in one process: the
window, the point of sale, the reports, and the LAN server an Admin's phone talks to. The product is becoming a
**shop server** that owns the database and a set of **clients** — the till on the counter PC, the Admin's phone,
and later a back-office screen — that hold no data and reach the server over authenticated HTTPS and WebSocket.
The single most important sentence in the new design is the one that makes the rest of it possible:
**only the server process opens the database file.** Everything else in this document follows from it.

## Kept, changed, removed

### Kept as-is (the work is sound and is reused, not rebuilt)

| Kept | Why it survives the change |
| --- | --- |
| `src/db/migrations/001`–`015` and every table they create | A live shop's data is in these tables. The migration plan extends the schema; it does not replace it. Every earlier table is preserved. |
| `src/currency/` — `formatMoney`, `parseMoney`, rounding, the lock guard | Money handling is already integer minor units end to end and already tested against 0-, 2- and 3-decimal currencies. None of that is a single-PC assumption. It moves, unchanged in behaviour, into the shared core. |
| `src/license/` — Ed25519 policy, machine binding, offline activation | Licences bind to the **server machine's** ID. Clients carry no licence. The existing licence code already treats the host as the licensed party, so binding it to the server rather than the PC is a rename of the owner, not a rewrite. |
| SQLite with WAL, `busy_timeout`, foreign keys on | The single-writer property is what makes a server process a sensible owner. It stays; it is now *enforced by the architecture* instead of merely being true because there was one process. |
| The `audit_log` table and its writer | Audit already records actor, action, device name, remote IP and time. The new `audit_signoffs` and `audit_flags` tables extend this record; they do not replace it. |
| `src/api/` Fastify HTTPS + WSS host, device pairing, TOTP, session tokens | This is already a server, and already authenticated. It is the seed of the real server rather than a prototype to discard. |
| The `mobile/` PWA | It is already a client that holds no database. It becomes one of several clients. |

### Changed (the same concept, under a different name or owner)

| Before | After | Consequence |
| --- | --- | --- |
| **Single-PC point of sale**: a sale is rung up and is immediately final | **Order + payment**: a client creates a `DRAFT` → `PENDING` order, the server owns `PAID`/`CANCELLED`/`EXPIRED`, and a stock `reservation` holds goods while an order is pending | A sale can no longer be created by a client directly. Stock is reserved, then committed by the server inside one transaction with optimistic locking. |
| **CASHIER** role | **ACCOUNT** (a person who may be signed in on a till) and **USER** (a person who may take orders and payments) | The role vocabulary gains a member and the till role is renamed. `CASHIER` is retained as a **deprecated alias resolved to `USER`**, so an existing shop upgrades without losing or reclassifying a single account. |
| **SUPERVISOR** approves returns, discounts and voids | **SUPERVISOR is audit-only**: reviews, signs off and flags; holds no operational authority | Supervisor approval of a *money movement* is removed. A supervisor may read the audit trail, sign off on a session, and raise a flag — nothing more. |
| The mobile host is an Admin-only add-on to a desktop app | **The LAN host is the server**, serving every client and the Admin phone | Mobile access is no longer a feature bolted onto the till; it is the same API every client uses, with a policy entry per route. |
| Roles checked in the UI and partly in host services | **Every request and every IPC channel checked on the server against one declarative policy table** | A route or channel with no policy entry is *refused*, not allowed. A test enumerates the registered surface and fails when an entry is missing. |
| Receipt numbers generated by SQLite column defaults on the sales row | **Numbers allocated by the server only**, sequential and unique | A client cannot choose, guess or duplicate a document number. |

### Removed (deliberately, and what replaces it)

| Removed | Replacement |
| --- | --- |
| The assumption that the process holding the window also holds the database | The server is the only process that imports the database module. A static check fails the build if any client-side code imports it. |
| A shared folder or SMB path as a way to "share the data" | Explicitly forbidden. Clients speak HTTPS/WebSocket to the server and nothing else. |
| Supervisor authority over money | Supervisor is audit-only. A supervisor sign-off is a recorded, append-only event, not a permission. |
| Any command-line step for the vendor or the customer | Unchanged rule, still in force, and now also covers the server: it starts and migrates itself. |
| Client-held licences | Clients never carry a licence. The server machine is the licensed machine. |

## The directory layout: what is moved, and what is not

The brief names a target layout: `/apps/server`, `/apps/client`, `/packages/core`, `/mobile`, `/cloud`,
`/installer`, `/buildstudio`, `/docs`. The repository today has a single `src/` tree, plus `mobile/`, `cloud/`,
`cloud-package/`, `installer/`, `buildstudio/`, `docs/`, `scripts/` and `tools/`.

The brief also carries a MIGRATION RULE that outranks the layout list: **reuse what exists; do not rebuild it.**
A `git mv` of the whole `src/` tree into `apps/` and `packages/` is not reuse. It is a rename of roughly 400
tracked files, and it is measured as follows:

- **76 files outside `src/`** name a `src/…` path — the Electron/Vite configs, the NSIS script and its checker,
  the release assembler, the Build Studio, the cloud package, 8 scripts, and the documentation.
- **~800 relative imports inside `src/`** would change depth, of which 154 point at `shared/`, 93 at `currency/`,
  92 at `services/` and 60 at `db/`.
- The alias set (`@shared`, `@main`, `@renderer`) is declared in three separate configs and is load-bearing for the
  build.

Doing that in the same phase that introduces a new schema, a permission policy and a database-ownership rule
would mean that when a test fails, nobody could tell whether the data model or the moved import was at fault.
Worse, it would be done on a Linux build agent with no way to compile the installer, so a broken path would be
discovered by the customer rather than by the suite.

**Decided:** the target layout is adopted **incrementally, in the direction the brief names**, and each step is
justified by the code that moves into it rather than by the shape of the tree:

| Target | Status after this phase | What it is |
| --- | --- | --- |
| `/packages/core` | **Created in this phase, and populated** | The code that a client and a server genuinely both need and that has no I/O: the role vocabulary, the single declarative permission policy table covering every action, route and IPC channel, and the money formatting/rounding rules re-exported from `src/currency`. It has no dependency on SQLite, Electron, Fastify or the filesystem, which is what makes it shareable at all. |
| `/apps/server` | **Deferred, with the boundary enforced now** | Today's server is `src/api/` (Fastify HTTPS + WSS) plus `src/db/`, `src/services/`, `src/license/`. This phase makes those the *only* code allowed to open the database, and proves it with a static check. The physical move to `apps/server` is a mechanical step that can be taken once the boundary is real — and the boundary is what matters, not the folder name. |
| `/apps/client` | **Deferred; the existing client is `src/renderer/` + `src/preload/`** | Already a client: it holds no database and reaches the host through typed IPC. Moving it before the server API replaces those IPC channels would move it twice. |
| `/mobile` | Exists, reused | The Admin PWA. Unchanged in this phase. |
| `/cloud`, `/installer`, `/buildstudio`, `/docs` | Exist, reused | No change in this phase. |

This is recorded in `docs/DECISIONS.md` as a decision, not left as an unstated compromise. The rule that keeps
it honest: **`/packages/core` may not grow an I/O dependency.** If something needs the filesystem, a socket or a
database handle, it does not belong in the shared package, and a test asserts that it imports none of them.

## What this phase builds

1. **The data foundations.** A migration (`016`) that adds every table the brief names — `role_seats`,
   `client_devices`, `sessions`, `orders`, `order_items`, `order_events`, `reservations`, `print_log`,
   `audit_signoffs`, `audit_flags` — extends `users` with `seat_no` and the widened role vocabulary, links
   `sales` to an order and a finaliser, and leaves every earlier table untouched.
2. **The permission foundations.** One table in `/packages/core` mapping every action, every API route and every
   IPC channel to the roles allowed to perform it, consulted by the server before the handler runs. A route or
   channel absent from the table is refused. A test enumerates the registered surface from the code that
   registers it and fails if anything is unpoliced.
3. **The ownership foundations.** One module opens the database. A static check proves no client-side file
   imports it, and a test proves the check fails when a client-side import is added.

## The rule that this phase must leave behind

A client cannot open the database **by any code path**, not merely by convention. That is the property the rest
of the product rests on: if a client can open the file, then two writers exist, the single-writer assumption
behind every transaction is false, and the permission table is decoration. It is therefore checked mechanically,
and the check is itself tested by breaking it on purpose.

## Divergence recorded in Phase 18: `orders.order_number` is allocated at creation

This document described `order_number` as staying NULL until finalisation, so a cancelled draft would burn no document
number. Phase 18 changed that, and the change is recorded here because this is the document that promised it.

**Why.** The workflow the brief describes is a conversation across a shop floor. A picker generates an order and reads
its number off an on-screen slip; an Account sees the same order arrive in a live queue and pays for it. Both halves have
to be able to name the order while it is still unpaid, and a number that appears only at payment cannot take part in
that conversation. So the number is allocated when the order is created.

**How.** From `document_sequences` (kind `ORDER`), the allocator migration 16 built for this and nothing had used yet:
one row per document kind, written only by the Server, with a trigger refusing a number that moves backwards. Not from
`MAX()` over `orders` — that would be a second allocator no trigger protects, and one that would silently disagree with
the receipt sequence if the same shape were ever reused for sales.

**What it costs.** A cancelled or expired order burns its number and leaves a gap in the sequence. This is accepted, and
accepted deliberately: gaps are normal in document numbering, and a sequence with none is a sequence somebody has been
closing up. An order number identifies a picking event, not money, so a gap is not an unaccounted-for sale — receipts
keep their own separate sequence, which still has no gaps because a receipt is only ever created by a completed sale.

`sales.order_id`, added by migration 16 and written from Phase 18, carries the link from an order to the sale it became.
It is NULL for a counter sale the Account built directly, which is most sales.
